# Confluence runbook publishing (F6.N)

Confluence is a **read-only consumer** of the Sentinel runbook catalog. The
source of truth is the git repository (`src/sentinel/plugins/teams/<team>/runbooks/`).
Every merge to `main` runs `scripts/runbook_confluence_publish.py`, which
walks the on-disk catalog, converts each runbook from Markdown to Confluence
storage format, and idempotently upserts one Confluence page per runbook,
keyed by a `sentinel_sha` page property.

Every runbook in Confluence carries a banner generated by the publish script
that points readers back to the source file in git. Confluence is a viewing
surface for non-engineering audiences; it is not an authoring surface.

## What this means in practice

This is the load-bearing message of this document, repeated for emphasis
because it changes how operators have to think about the catalog.

* **Edits made directly in Confluence are discarded on the next publish.**
  The publish script does not read the current page body; it overwrites it
  with the converted Markdown from the git tree. Anyone who edits a runbook
  through the Confluence UI will see their change vanish the next time
  someone merges a runbook PR.
* **The only ingestion path for new runbooks is a PR to the git repo.** Two
  flavours of PR exist:
  - hand-authored runbooks committed to
    `src/sentinel/plugins/teams/<team>/runbooks/<runbook-id>/` by an engineer;
  - auto-generated draft PRs opened by the F6.M flywheel
    (`scripts/runbook_gap_flywheel.py`) on a fresh
    `flywheel/runbook-gap-<fingerprint>` branch when the no-match clusterer
    crosses its threshold.
  Either way, the catalog grows through git, never through Confluence.
* **If someone needs to fix a runbook, they edit the file in git, not in
  Confluence.** The right path for a typo, a stale check, or a new
  remediation tip is a PR against the runbook directory. The wrong path
  is the Confluence "Edit" button.
* **The publish job is not a sync.** It is a one-way push from git to
  Confluence. There is no reverse path, no merge, no conflict resolution.

If you find yourself wanting to change a runbook on the Confluence side,
that is the signal: open a PR against the file in git.

## Setup

The publish script reads four required environment variables and one
optional one. All of them are also wired as GitHub Actions secrets on the
repository so the CI workflow can authenticate.

```text
CONFLUENCE_BASE_URL    # e.g. https://acme.atlassian.net/wiki
CONFLUENCE_USER        # the publishing service account's email
CONFLUENCE_TOKEN       # API token for that service account
CONFLUENCE_SPACE_KEY   # the space where runbooks live (e.g. RUNBOOKS)
CONFLUENCE_PARENT_PAGE_ID  # optional: parent page that hosts each runbook
```

What each one does:

* `CONFLUENCE_BASE_URL` -- the wiki host. The trailing `/wiki` is part of
  the Atlassian Cloud URL shape; on-prem deployments may differ.
* `CONFLUENCE_USER` -- the email of the service account that owns the
  upserts. Use a dedicated service account so the audit trail in
  Confluence is unambiguous; never use a human author's account.
* `CONFLUENCE_TOKEN` -- the API token for the service account, generated
  in Atlassian's "Manage account -> Security -> API tokens" UI.
* `CONFLUENCE_SPACE_KEY` -- the Confluence space key (the short identifier,
  not the display name). Visible in the URL as `/spaces/<KEY>/pages`.
* `CONFLUENCE_PARENT_PAGE_ID` -- optional. When set, every runbook page is
  created as a child of this page so they group together in the space tree.
  When unset, runbooks land at the space root.

For local development, set the four required vars in `.env` (see
`.env.default` for the canonical list). For CI, store them as repository
secrets and reference them from the workflow:

```yaml
name: runbook-publish

on:
  push:
    branches: [main]

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: just install
      - run: just run-runbook-publish
        env:
          CONFLUENCE_BASE_URL: ${{ secrets.CONFLUENCE_BASE_URL }}
          CONFLUENCE_USER: ${{ secrets.CONFLUENCE_USER }}
          CONFLUENCE_TOKEN: ${{ secrets.CONFLUENCE_TOKEN }}
          CONFLUENCE_SPACE_KEY: ${{ secrets.CONFLUENCE_SPACE_KEY }}
          CONFLUENCE_PARENT_PAGE_ID: ${{ secrets.CONFLUENCE_PARENT_PAGE_ID }}
```

## What happens when

A short tour of the lifecycle as observed from operations.

### On merge to main

1. The `runbook-publish` workflow runs `scripts/runbook_confluence_publish.py`.
2. The script walks the catalog via `discover_runbooks()`, skipping any
   runbook whose id starts with `_` (private templates) or `AUTOGEN-`
   (gap-flywheel scaffolds in draft).
3. For each remaining runbook, the script computes the catalog
   `content_sha`, fetches the current Confluence page (if any), and
   compares. If the page already carries a `sentinel_sha` property
   matching the catalog hash, the page is skipped without a network write.
4. If the SHAs differ (or the page does not yet exist), the script
   converts the runbook Markdown to Confluence storage format and upserts
   the page, refreshing the `sentinel_sha` property. The page body is
   replaced entirely; previous content is not preserved.
5. The script logs `runbook_confluence_publish_succeeded` with the
   per-runbook upsert counts. Exit code 0 on success, 1 if any upsert
   raised. The CI step status mirrors the exit code.

### When unconfigured

If any of `CONFLUENCE_BASE_URL`, `CONFLUENCE_USER`, `CONFLUENCE_TOKEN`,
or `CONFLUENCE_SPACE_KEY` is empty, the publish script logs
`runbook_confluence_publish_skipped_unconfigured` and exits 0. The CI
step succeeds without doing anything. This follows the firm-wide
vendor-adapter convention: a missing-credential deployment must not
break the merge pipeline.

### When a Confluence edit accidentally happens

Suppose someone clicks "Edit" in Confluence and changes a runbook body
directly. The next time `main` ships any runbook PR (any change at all,
even an unrelated runbook), the publish job runs, the script overwrites
that page with the catalog version, and the manual edit is gone.

The remediation is simple but worth saying explicitly: **redo the
change as a PR against the file in git**. Do not retry in Confluence;
the result will be the same. There is no recovery path for the
overwritten content other than re-applying it through the source repo.

If a Confluence-side edit is detected as having dropped real signal
(e.g. someone was correcting a serious factual error), grab the page
history in Confluence to recover the diff, then port the change into a
git PR.

## Troubleshooting

Common failure modes and remediation.

* **Auth failure (`401 Unauthorized` / `403 Forbidden`).** The API
  token is expired, revoked, or pointing at the wrong account. Rotate
  the token through Atlassian's account UI and re-set
  `CONFLUENCE_TOKEN` in both `.env` (local) and the GitHub Actions
  secret (CI).
* **Wrong space (`404 Not Found` on parent page lookup).** Either
  `CONFLUENCE_SPACE_KEY` is mistyped, the space was renamed, or the
  service account lacks permission to read it. Verify the space key
  by visiting the space in Confluence and copying it from the URL,
  and confirm the service account has at least "Add" permission on
  pages in that space.
* **Storage-format conversion failure.** The Markdown -> Confluence
  storage converter rejects payloads that contain malformed HTML
  fragments or unsupported Markdown extensions. The error log carries
  the runbook id and a snippet of the offending text. Inspect the
  runbook body, simplify the Markdown construct, and reland the change
  via PR. The publish job is per-runbook resilient: a bad runbook
  fails its own upsert and the script continues with the rest before
  exiting non-zero.
* **`sentinel_sha` property not found on existing page.** This
  happens when a page was created manually before the F6.N publisher
  was wired. The script will detect the missing property and treat
  the page as a fresh upsert (replacing the body). No remediation
  required; the next run reconciles.
* **Page exists but body never refreshes.** Either the page id moved
  (rare; Confluence preserves ids across renames) or the
  `sentinel_sha` property is stale-but-matching. To force a refresh,
  bump the runbook's `last_validated` field in frontmatter and merge
  the change -- the F6.E pre-commit hook will recompute the
  `content_sha` and the next publish will treat the page as drifted.
* **Auto-flywheel runbook leaked into Confluence.** Should not happen:
  the publish script skips any runbook whose id starts with
  `AUTOGEN-`. If you see one, check whether the runbook was renamed
  out of the prefix without being graduated through code review.
